    ✕Only the happy path was tested, and the first production timeout paid out twice.
    ✓Run the full test matrix: timeouts, duplicates, rejects, callbacks, cutoffs and signature failures, with the raw request and response kept for each case.

    🏁Done when: Every case in the test matrix passes with its traces, and the partner certifies.

  6. 6

API review & credentials

Partner API review questions

  1. Is the payout API synchronous, asynchronous with a callback, or both? Which signal is final?
  2. What is the full status model? Which states are final, and can a final state still change (returns, reversals)?
  3. Which field carries idempotency, how long is it honoured, and what does a duplicate return?
  4. Is there a status enquiry by our reference, and what are its rate limits?
  5. How are callbacks signed and retried? Is ordering guaranteed? Which IP ranges send them?
  6. Is account or alias validation available before sending, and does it return the account name?
  7. What are the per-transaction and daily limits, batch windows, cutoffs and holidays?
  8. What is the full error list? ISO 20022 reason codes or proprietary, and which are final?
  9. How do prefunding, settlement and the settlement report work, and when do they arrive?
  10. What screening does the partner run, and how does a compliance hold or reject reach us?

Cryptography pitfalls I check for
  • AES-256-GCM authenticates the data; CBC does not, so it needs a separate MAC and is open to padding-oracle mistakes.
  • Hex versus Base64: agree the encoding of keys, IVs and signatures; a mismatch looks like "invalid signature".
  • Sign and verify the raw body bytes, not re-serialised JSON, and include a timestamp to stop replays.
  • RSA for signatures or key wrapping, with the padding scheme written into the spec.

    Rails primer: what I explain to engineers and business leads

    Clearing vs settlementClearing exchanges and confirms the payment messages; settlement moves the funds between institutions. A "credited" status is not the same as settled.
    Instant vs deferred batchInstant rails confirm in seconds, all day. Batch rails clear in windows, so cutoffs and holidays decide the credit date.
    Alias vs accountAn alias (UPI ID, mobile number) is resolved to an account by the rail or a directory; validating it first avoids most rejections.
    ISO 20022 vs ISO 8583ISO 20022 (pacs.008 credit, pacs.002 status, camt.05x statements) for account rails; ISO 8583 (MTI 0200/0210, response code in field 39) for card-based payouts.

    Failure handling

    What breaks in production, how we spot it, and what we do instead of guessing.

    Timeout on create

    DetectNo response, or a 5xx, after sending the payout

    FallbackThe state is unknown, not failed. Query status by our reference; retry only with the same idempotency key if the partner confirms it never arrived.

    Repeated or out-of-order callbacks

    DetectSame event again, or an older status after a newer one

    FallbackDeduplicate events, not the payout. Allow valid changes such as a return, never move a final status backwards, and reconcile with the status API.

    Rejection spike on one corridor

    DetectRejection rate for one reason code above its baseline

    FallbackQuery the data, check our own changes first, then escalate with evidence. Pause or re-route if customers are affected.

    Unmapped error code

    DetectA partner code with no entry in the mapping

    FallbackHold as pending, query status, alert, and add the mapping with the partner's written meaning.

    Missed cutoff or holiday

    DetectBatch payout submitted after the window

    FallbackShow the real expected credit date. Queue it; don't mark it failed or resend it.

    Compliance hold or sanctions match

    DetectHold status or a regulatory reject (RR04)

    FallbackRoute to Compliance with the evidence. Never auto-retry or resend on another rail to get round it.

    Run & escalate

    From transaction data to an argument

    Rejection rate by reason code, this week against the four weeks before. Table and column names are illustrative.

    -- Rejection rate by reason code: this week vs the prior 4 weeks
WITH w AS (
  SELECT status, reason_code,
         created_at >= now() - interval '7 days' AS this_week
  FROM   payouts
  WHERE  partner_id = 'corvid' AND corridor = 'US-PH'
    AND  created_at >= now() - interval '35 days'
)
SELECT reason_code,
  round(100.0 * count(*) FILTER (WHERE this_week)
        / nullif((SELECT count(*) FROM w WHERE this_week), 0), 2)     AS pct_this_week,
  round(100.0 * count(*) FILTER (WHERE NOT this_week)
        / nullif((SELECT count(*) FROM w WHERE NOT this_week), 0), 2) AS pct_prior_4_weeks
FROM   w
WHERE  status = 'REJECTED'
GROUP BY reason_code
ORDER BY pct_this_week DESC;

    Recurring friction → platform roadmap
    • Unmapped codes flagged automatically, not found in tickets.
    • Checksums (IBAN, CLABE) and alias formats validated before send.
    • Cutoff and holiday calendars per rail held in configuration.
    • Certificate and key expiry monitored, with alerts well ahead.

    Key best practices

    Integration
    🔁Unknown is not failed

    After a timeout, query status. Never create a second payout to "retry".

    🧷One idempotency key per payout

    Reuse it on every retry, so a duplicate can never pay twice.

    🔒Verify, then act

    Check the callback signature over the raw body before changing any status.

    ✅Validate before money moves

    Checksums, alias formats and name checks catch most rejections up front.

    Ownership
    📊Escalate with data

    A query, sample traces and our own changes ruled out, in every escalation.

    🧩Fix the cause

    A problem seen twice becomes a platform change or a roadmap item.

    🗣️Two audiences, one page

    Rails for engineers, contracts and SLAs for business leads, in the same note.

    📅Track every expiry

    Certificates, keys and secrets, with alerts long before they lapse.
